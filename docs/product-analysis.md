# Obelisk 产品分析

## 一、定位

Obelisk 是面向编程 Agent 用户的本地记忆基础设施。它采集 Claude Code、Codex、Kimi Code、Pi、DeepSeek Harness 五种编程 Agent 在本地产生的全部会话历史，整理为统一的可查询索引。Agent 通过命令行检索这个索引，用真实的历史记录回答关于此前工作的问题；人通过桌面应用回看历史会话、管理记忆、查看用量统计与周期复盘。所有数据保存在本机，全部处理在本地完成。

## 二、问题

编程 Agent 的每次会话都留下完整记录：用户意图、推理过程、每次文件修改、每条命令及其输出、每次失败与重试。这些记录以 JSONL 文件形式存放在本地，内容完整，人和 Agent 都无法针对它们提问。

这带来两个后果。Agent 跨会话失忆，无法回答"上次这个问题怎么解决的"，只能重新执行已经执行过的探索，包括已经失败过的路径，同样的错误会重复出现。人无法回看历史：想回忆"当时为什么这样改""那次试过哪些方案"，只能人工翻找原始日志，实际上不会去做。

Obelisk 的判断：会话历史是有价值的资产，损失的原因是记录无法被检索；解决方案是给既有记录建立索引，并为记忆的存取制定可验证的规则。

## 三、核心逻辑

核心逻辑是三个动作：全面记录事实；需要时通过脚本查询历史（回忆）；把有效的查询结论保存为记忆。

### 3.1 记录：全部历史自动进入索引

全部历史自动进入索引，不需要选择或批准。索引粒度覆盖会话、消息、工具调用及其结果、子 Agent、工作流、摘要，并保留消息之间的父子链。五种 Agent 的记录共用同一结构，每条记录标注产生它的 Agent 产品。Agent 据此可以区分一条历史出自哪个工具、哪次会话，以及这条历史是否就是自己当前正在进行的会话。其余功能都建立在这份索引之上。

### 3.2 查询：Agent 写脚本，读 JSON 结果

Agent 需要历史时，写一小段 JavaScript 查询脚本，经命令行执行，读取返回的 JSON 结果，这是回忆的完整过程。产品提供两类检索：文本检索做关键词全文匹配；另有结构化查询，按文件查修改历史、按失败筛选工具调用、展开工作流执行树、按项目分支和时间过滤，官方指导文档要求优先使用。语义理解由 Agent 承担：它把用户的自然语言问题翻译为检索词、组合条件、依据结果调整查询。

回忆由 Agent 主动发起。Obelisk 是被调用的本地工具，只在收到查询时返回数据；何时查询由 Agent 自己判断：用户问到过去的工作、Agent 发现自己缺少上下文、用户要求存取记忆。检索与引用的动作发生在对话之内，用户可见。产品将“隐式记忆、环境记忆、自动召回”三个词列为禁用表述。

每次查询会标记发起查询的那个会话。Agent 被要求把当前会话与历史证据区分开，不得把当前会话当作历史证据引用。无法确认发起查询的是哪个会话时，标记为未知。

### 3.3 记忆：保存有效的查询结论

当一次检索产出反复有用的结论，Agent 可以提议将其保存为记忆，保存需经用户批准。保存下来的记忆包含三部分：结论本身、来源锚点（结论取自哪次会话的哪一段消息）、登记记录（创建时间，可撤销，撤销需附原因）。记忆的用途是加速重复查询。被批准的记忆可以被追溯、核实、删除。

### 3.4 三个动作的主次

记录是基础，独立成立：从未保存过任何记忆，产品依然完整可用。查询是历史数据的主要使用方式。记忆是可选的加速手段，用户批准是唯一的保存路径。产品的主要投入在记录与查询上。

## 四、关键取舍

### 4.1 记忆以查询方式工作

Obelisk 服务五种编程 Agent，各产品的会话机制互不兼容，唯一通用的集成点是 Agent 执行一条命令，记忆因此以查询方式工作。部分记忆产品通过向上下文注入内容实现自动召回。查询方式有三个好处：其一，Agent 取得记忆后先核实再使用，错误结论可以被当场识别；自动注入的记忆直接进入上下文，用户无从察觉是哪条记忆在起作用。其二，记忆只在需要时占用上下文，常驻注入会占用当前任务的空间。其三，记忆何时被使用可见、可追问。

### 4.2 语义理解放在提问方

文本检索做关键词全文匹配，语义理解由 Agent 在查询时完成：翻译检索词、多轮调整、综合结果。同类产品常把语义检索做进索引（向量检索）。关键词检索的收益有三点：结果可解释，命中即字面匹配；检索在本地完成，无需部署模型服务；检索层简单可靠。代价：检索质量依赖 Agent 的查询能力；对中文这类分词不友好的语言，Agent 需要先转译为英文关键词，官方指导文档包含这一指导。

### 4.3 以写代码的方式查询

Agent 直接写一段查询代码，运行后取得 JSON。运行时接口只有四个动词：构建索引、文本搜索、查询、记忆写入。产品预置了一组结构化查询：按文件查修改历史、按失败筛选工具调用、展开工作流执行树、按项目和分支与时间范围过滤；官方指导文档要求优先使用预置查询。预置查询覆盖不到的问题由 Agent 在脚本里组合：跨表关联、聚合、多步筛选，或直接写只读 SQL。代价是对 Agent 的编程能力有要求，对较弱模型不友好。

### 4.4 Agent 与人读写同一份数据

Agent 侧（命令行加指导文档）与人侧（桌面应用）读写同一个本地数据库。Agent 的回答取自这份索引；人回看历史，应用里打开的也是这份索引里的会话。用户想核对 Agent 说的"上次怎么修的"，直接打开对应会话即可，两边数据一致，核对不依赖同步。这是第二节第二个后果（人无法回看历史）的解决方案。人界面承担会话浏览、记忆管理、用量统计与周期复盘；复盘卡片与活跃度统计属于第二优先级，它们为历史数据创造了检索之外的使用方式。

## 五、产品边界

产品的边界由设计原则决定：证据先于结论；默认人类可读，协议与存储细节按需展开；推断与观测事实分开呈现；长会话保持可扫描；用户对历史与记忆的掌控权始终可见。产品同时给出四类反面参照：聊天记录浏览器、终端日志墙、AI 摘要仪表盘、脱离来源证据的装饰性分析。聊天记录浏览器和终端日志墙把原始记录直接暴露当作主要体验，与可读性和密度原则冲突；AI 摘要仪表盘和装饰性分析交付结论时切断来源，与证据原则冲突。

## 六、风险与局限

产品定义的成功标准：用户从一个回忆性的问题出发，低摩擦、高置信地到达确切的历史证据。以下风险逐条对照这个标准评估。

成功标准以“用户提出回忆性问题”为起点，整个产品的价值依赖这个行为的发生。用户很少向 Agent 问起历史，产品就没有兑现机会。项目文档没有提供提问频率的数据，这是一个待验证的前提。桌面应用的统计与复盘功能提供了检索之外的使用方式，主场景仍是回顾性提问。

记忆层的功能是加速重复查询。记忆稀疏时用户退回查询路径，成功标准依然达成，损失的只是重复查询的效率。“记忆稀疏可以接受”的依据在这里：成功标准不经过记忆层。

转录格式是外部依赖。五种 Agent 的转录格式不受 Obelisk 控制，格式变更需要适配器跟进；适配失效期间索引停止更新，查询返回的证据落后于实际历史，“确切的历史证据”对新发生的会话不成立。各 Agent 的记录语义不一致（能否证明撤销、是否有分支、是否有工作流元数据），统一到同一结构时部分信息丢失，项目文档对每种 Agent 的差异做了公开说明。

分发与语言影响标准的两个成分。预构建桌面应用目前仅覆盖 macOS，其他平台的人侧功能需从源码运行，“人回看历史”在非 macOS 平台不可用；中文检索依赖 Agent 先转译英文关键词，检索环节增加一道转换，转译错漏会造成漏检，“低摩擦、高置信”对中文用户打折。

全部历史集中于一个本地数据库。产品的前提是数据留在本机、由用户掌管，项目将转录内容一律视为不可信输入；这个数据库是安全上最集中的目标，维护失效时暴露的是用户的全部工作历史。

## 七、本质

Obelisk 把记忆放在模型外部，做成可追溯、由人掌管的基础设施。已经存在的完整记录被整理为可查询的索引；保存为记忆的每个结论带来源、经批准、可撤销；回答中引用的记忆可以回溯到事实记录。产品的差异化来自这三条规则的执行。
